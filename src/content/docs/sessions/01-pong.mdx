## MonoGame & Tooling

MonoGame is a _framework_. It gives us libraries for graphics, input, audio, content loading
and math, but it has no editor, scene graph or entity system like an engine such as Unity
has. We write those parts ourselves, and that makes it a good fit for a course about game
architecture.

Tooling used in the course:

## Game Loop

Every game runs a loop: process input, update the simulation, render, repeat. In MonoGame,
the `Game` class runs the loop and calls your `Update` and `Draw` overrides.

![Lifecycle of a MonoGame game](../../../assets/session01/monogame-lifecycle.png)

_Figure 1-1: Lifecycle of a MonoGame game_

Unlike Unity, there is no hidden object system calling `Update` on your behalf. `Game1`
gets one `Update` and one `Draw` call per frame, and everything else in your game only runs
if you call it from there. For more detail, see
[What is the Game Loop](https://docs.monogame.net/articles/getting_to_know/whatis/game_loop/index.html).

`Update` changes the state of the world, and `Draw` only reads that state and renders it.
Because they are kept apart, the simulation and the rendering can run at different rates,
which is the idea behind a fixed timestep.

Rendering itself uses a _double buffer_: we draw into a back buffer that isn't visible,
and MonoGame presents it (`GraphicsDevice.Present()`, called at the end of `Draw`) so the
player never sees a half-drawn frame. See
[Double Buffer](https://gameprogrammingpatterns.com/double-buffer.html) for the pattern.

### Fixed vs. variable timestep

- **Variable timestep:** update once per rendered frame and scale all movement by the
  elapsed time (`deltaTime`). Simple, but the simulation behaves slightly differently at
  different frame rates. A long frame (the window is dragged, the computer stalls) gives a
  large `deltaTime`, and a fast object can jump straight through a thin wall in one step.
- **Fixed timestep:** update the simulation in fixed-size steps (e.g. 60 per second),
  running zero, one or several steps per rendered frame. This makes the simulation
  deterministic and stable, at the cost of some complexity. If one step takes longer than
  the time it simulates, the game falls further behind every frame; engines limit how many
  steps they catch up, and MonoGame then runs the game in slow motion. MonoGame uses a
  fixed timestep by default (`IsFixedTimeStep = true`).

### Try it

Lower the tick rate and compare the two lanes. Both simulations run at the same rate. The
bottom lane blends the last two ticks using `accumulator / dt`, so its motion looks smooth
even when the simulation updates only a few times per second.

## Content Pipeline

Raw assets (fonts, images, sounds) aren't loaded directly. When the game builds, the
**content builder** converts them into an optimized format (`.xnb` files) for the target
platform, and at runtime we load them with `Content.Load<T>("name")` in `LoadContent`.

```mermaid
flowchart LR
    A["Raw assets<br/>Assets/"] --> B["Builder.cs<br/>rules in C#"] --> C["Content builder<br/>runs on build"] --> D[".xnb files<br/>bin/…/Content"] --> E["ContentManager<br/>Content.Load&lt;T&gt;()"]
```

The rules for building assets are ordinary C# in `Content/Builder/Builder.cs`. For Pong, we
need fonts and sounds:

```csharp title="Builder.cs"
public class Builder : ContentBuilder
{
    public override IContentCollection GetContentCollection()
    {
        var content = new ContentCollection();

        // A .spritefont describes a font (e.g. a .ttf next to it), a size and a set of
        // characters. The builder renders those characters into a texture.
        content.Include<WildcardRule>("*.spritefont", new FontDescriptionImporter(), new FontDescriptionProcessor
        {
            PremultiplyAlpha = true,
            TextureFormat = TextureProcessorOutputFormat.Compressed,
        });

        // Short sounds become sound effects, loaded fully into memory.
        content.Include<WildcardRule>("*.wav", new WavImporter(), new SoundEffectProcessor
        {
            Quality = ConversionQuality.Best,
        });

        return content;
    }
}
```

Each game project imports `Content/BuildContent.targets`, which runs the builder before
compiling. To add an asset, put it in `Content/Assets`; if no rule matches it, add one. All
Pong steps share that folder: step 3 swaps the plain `sans` font for the retro `font`
in code. See
[Content Builder Project](https://docs.monogame.net/articles/getting_started/content_pipeline/content_builder_project.html).

## Drawing to the Screen

- MonoGame's 2D coordinate system has its origin in the **top-left** corner, with Y
  pointing **down**.
- All 2D drawing goes through a `SpriteBatch`, between `Begin()` and `End()`. `Draw` doesn't
  draw straight away: the sprite batch collects the calls, and `End()` sends them to the
  graphics card in as few batches as it can. A batch ends whenever the texture changes, which
  is why [Snake](../03-snake/#texture-atlases) puts its images in one texture. `Begin()` takes
  the settings for everything up to `End()`: the transform matrix, the texture filtering and
  the blending.
- Pong doesn't need image assets, but we still need a texture to draw rectangles. A 1×1
  white texture stretched to any `Rectangle` does the job:

```csharp
_pixel = new Texture2D(GraphicsDevice, 1, 1);
_pixel.SetData([Color.White]);

_spriteBatch.Draw(_pixel, new Rectangle(x, y, width, height), Color.White);
```

- Text is drawn with a `SpriteFont` asset and `SpriteBatch.DrawString()`.
- **Virtual resolution:** we render the game at a fixed internal resolution and scale it
  to the window with a transform matrix passed to `SpriteBatch.Begin()`. The game logic
  never needs to know how big the window is.
- **Texture filtering:** use `SamplerState.PointClamp` for crisp pixel art when scaling up.

See [What is a sprite?](https://docs.monogame.net/articles/getting_to_know/whatis/graphics/WhatIs_Sprite.html).

## Input

We poll the keyboard every frame:

```csharp
KeyboardState keyboard = Keyboard.GetState();

if (keyboard.IsKeyDown(Keys.W))
    _player1Y -= PaddleSpeed * deltaTime;
if (keyboard.IsKeyDown(Keys.S))
    _player1Y += PaddleSpeed * deltaTime;
```

MonoGame has no built-in "was this key _just_ pressed?". We emulate it by comparing with
last frame's state:

```csharp
bool enterPressed = keyboard.IsKeyDown(Keys.Enter) && !_previousKeyboard.IsKeyDown(Keys.Enter);
_previousKeyboard = keyboard;
```

## DeltaTime & Velocity

`deltaTime` is the time since the last update, in seconds:

```csharp
float deltaTime = (float)gameTime.ElapsedGameTime.TotalSeconds;
```

Multiplying movement by `deltaTime` makes speed independent of frame rate: a paddle moving
at 200 units per second moves 200 units per second, whether the game runs at 30 or 144 FPS.
_Velocity_ (a direction and a speed, e.g. a `Vector2`) lets the ball keep moving without
input.

## Encapsulation & the Update Method Pattern

Our first version puts everything in `Game1`. As soon as we have a paddle and a ball, we
move their data and behaviour into `Paddle` and `Ball` classes, each with its own `Update`
and `Draw` methods. `Game1` then just calls them. This is the
[Update Method](https://gameprogrammingpatterns.com/update-method.html) pattern: each
object knows how to simulate one frame of its own behaviour.

It has costs too. Objects are updated one after another, so the order matters: an object
updated early sees the others as they were last frame, and one updated late sees them
already moved. Objects that interact, like the ball and the paddles, need a reference to
each other, or a place like `Game1` that checks them together. Every object is updated every
frame even when it has nothing to do. And adding or removing objects while looping over them
needs care ([Angry Birds](../08-angry-birds/#destroying-safely) shows how).

## Collision Detection (AABB)

Axis-Aligned Bounding Boxes are rectangles that never rotate. Two of them overlap if they
overlap on both axes:

```csharp
public static bool AABB(Rectangle a, Rectangle b)
{
    return a.Left < b.Right &&
           a.Right > b.Left &&
           a.Top < b.Bottom &&
           a.Bottom > b.Top;
}
```

(MonoGame provides the same check as `Rectangle.Intersects()`, but it's worth writing
yourself once.)

## Game State

Pong has distinct phases: _start_, _serve_, _play_ and _done_. Today we track them with a
simple `string` field and `if`-checks in `Update` and `Draw`. That is fine for four states,
but every new state means another `if` in each method. In
[Flappy Bird](../02-flappy-bird/) we replace it with a state machine.

## Sound Effects

`SoundEffect` is for short clips (hits, jumps, clicks). They are loaded fully into memory
and several can play at once. Longer music uses `Song` (next session).

Make your own 8-bit sounds with [bfxr.net](https://www.bfxr.net/).

## Exercises

Build Pong step by step:

0. **An empty game:** clone [gar-games](https://github.com/Metamate/gar-games), open
   `01-pong/Pong0` (an empty MonoGame game set up with the content builder) and run it from
   the `01-pong` folder with `dotnet run --project Pong0`. Do the exercises in `Pong0`;
   step `PongN` is a solution to exercise N, to compare with when you're done.
1. **Text on screen:** draw "Hello, MonoGame!" centred on a black 1280×720 window. The
   font is already in `Content/Assets`: load it with `Content.Load<SpriteFont>("sans")`,
   and centre the text with `MeasureString`.
2. **Virtual resolution:** draw the game at 432×243, scaled to fit a resizable window,
   with point filtering. Scale by the smaller of the two ratios (window width / 432,
   window height / 243) so nothing is stretched, and centre the result with
   `GraphicsDevice.Viewport`: black bars fill the rest. Recalculate when
   `Window.ClientSizeChanged` fires.
3. **Rectangles from a pixel:** draw two paddles and a ball, stretched from one white
   pixel. Switch to the retro font (`"font"`, also in `Content/Assets`) and the
   background colour `(40, 45, 52)`.
4. **Input and delta time:** W/S and Up/Down move the paddles, at the same speed whatever
   the frame rate.
5. **A moving ball:** launch the ball in a random direction on Enter. A `string` field
   remembers the game's mode (`"start"` or `"play"`), and the start mode shows "Press
   Enter to launch the ball". Keep the paddles on screen (`Math.Clamp`).
6. **The Update Method:** refactor into `Paddle` and `Ball` classes using the Update Method
   pattern. The game must behave exactly as before.
7. **Collisions and the bounce:** bounce off paddles and walls with AABB. Where the ball
   hits the paddle sets the new angle: straight back from the middle, steeply from the
   ends. Speed up the ball by 10% on each paddle hit.
8. **Scoring:** keep and display the score in a bigger font (`"font-big"`).
9. **A serve mode:** the player who was scored on serves next.
10. **A winner:** add a _done_ mode when a player reaches 10 points.
11. **Sound effects:** add distinct sounds for paddle hit, wall hit and score. Three are
    in `Content/Assets/sounds`, or make your own with bfxr.

## Check Yourself

<details>
<summary>What is the difference between a game engine and a game framework?</summary>

An engine is a complete environment: editor, scene and object model, and a loop that calls
your scripts. A framework like MonoGame is a set of libraries. You write the game's
structure yourself, including the loop's contents.

</details>

<details>
<summary>Why do we multiply movement by deltaTime?</summary>

So that movement per second is the same no matter how many frames are rendered per second.

</details>

<details>
<summary>Why is a string field a fragile way to store game state?</summary>

Typos aren't caught by the compiler, every `Update`/`Draw` needs an `if`-chain over all
states, and adding a state means editing all of those chains.

</details>
